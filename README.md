# submodule-hook

Git-хуки на Python (pre-commit + pre-push): держат сабмодули на коммитах, закреплённых
в `env.yml`, не дают конфигу и сабмодулю разъехаться и не пускают в remote висячие
коммиты сабмодулей. Идеологический наследник auto-version-hook: тот же стек
(Python + PyYAML, никаких других зависимостей), те же коды возврата, тот же
`scripts/install.sh`.

Зачем: сабмодуль «уезжает», когда разработчик переключил его (или подтянул мастер),
а `env.yml` с закреплённым коммитом остался старым — или наоборот, конфиг обновили,
а сабмодуль нет. Инвариант, который обеспечивает хук: **закреплённый в `env.yml`
коммит и коммит сабмодуля в ветке совпадают; переключение сабмодуля — это всегда два
изменения в одном коммите (сабмодуль + конфиг)**.

## Как это работает

На каждый сабмодуль — три SHA:

```
env.yml → submodules[].commit_sha ... CONFIG    что закреплено конфигом
git index → <folder> ............... CURRENT    что поедет в этот коммит
origin/<lookup_branch> → <folder> .. TARGET     что в защищённой ветке сейчас
```

При каждом коммите:

1. merge-коммиты пропускаются (`skip_merges`, по умолчанию true);
2. нет секции `submodules:` в `env.yml` — хук молча выходит (код 0);
3. обновляются lookup-ветки (`git fetch <remote> <lookup_branch>`, по одной на каждую
   уникальную), `TARGET` читается через `git ls-tree`;
4. `CURRENT` читается из индекса суперпроекта — ровно то, что этот коммит закрепит;
5. жёсткая проверка: `CONFIG` против `CURRENT` — расхождение блокирует коммит;
6. мягкая проверка: `CONFIG` против `TARGET` — расхождение предупреждает.

Таблица решений:

| `CONFIG` vs `CURRENT` | `CONFIG` vs `TARGET` | Вердикт |
|---|---|---|
| совпадают | совпадают | ✅ «сабмодуль не изменен, остаёмся на прежнем коммите» |
| совпадают | различаются | ⚠️ «после влития этой ветки сабмодуль в `<lookup_branch>` переключится: `TARGET` → `CONFIG`» |
| различаются | совпадают | ❌ блок: переключи сабмодуль (готовая команда в сообщении) или обнови конфиг |
| различаются | различаются | ❌ блок + предупреждение из строки выше; если `CURRENT == TARGET` — подсказка «конфиг отстал: обнови `commit_sha`, сабмодуль не откатывай» |

SHA сравниваются по префиксу: короткий `12351adf` в конфиге равен полному `12351adf…`
в ветке. Валидны hex-SHA от 4 до 40 символов; теги и имена веток не принимаются.

Вторая половина инструмента — pre-push хук против висячих коммитов сабмодулей,
см. «Висячие коммиты (pre-push)».

## Сообщения хука

Ошибка — конфиг и ветка разошлись (коммит блокируется, код 1):

```
$ git commit -m "feature work"
submodule-hook: libs/api-clients — конфиг и ветка разошлись
    env.yml закрепляет 12351adf, в коммит поедет 9a4c02e4
    переключи сабмодуль на коммит из конфига:
        cd libs/api-clients && git switch --detach 12351adf && git add libs/api-clients
    или, если переключение осознанное, обнови конфиг: commit_sha: 9a4c02e4
    подсказка: 9a4c02e4 — текущий коммит в origin/master, конфиг просто отстал;
    в этом случае обнови commit_sha, а сабмодуль не откатывай
```

Подсказка про `origin/master` появляется только когда `CURRENT == TARGET` — то есть
ветка несёт ровно то, что уже в защищённой ветке, и откатывать сабмодуль по команде
выше было бы ошибкой.

Предупреждение — влитие переключит сабмодуль в защищённой ветке (коммит проходит):

```
$ git commit -m "bump api-clients"
submodule-hook: libs/api-clients — закреплён 12351adf
submodule-hook: libs/api-clients — после влития ветки сабмодуль в master
    переключится: 9a4c02e4 -> 12351adf
```

Всё хорошо:

```
$ git commit -m "feature work"
submodule-hook: libs/api-clients — не изменен, остаёмся на 12351adf (как в master)
```

## Висячие коммиты (pre-push)

Pre-commit гарантирует, что пин и указатель едут вместе, но не знает, существует ли
коммит сабмодуля на его собственном remote: можно забыть запушить сабмодуль (или
мейнтейнер сабмодуля сделает force-push и коммит исчезнет) — суперпроект уедет с
gitlink'ом в никуда, и клонирование/CI сломаются у всех.

Поэтому `install.sh` ставит и второй хук — pre-push (`submodule-hook --push`). Перед
пушем он для каждого закреплённого в `env.yml` сабмодуля проверяет, что все коммиты
сабмодуля, на которые ссылаются пушемые коммиты и указатели пушемых веток, достижимы
из ветки на remote сабмодуля:

```
git -C <folder> fetch && git -C <folder> branch -r --contains <sha>
```

Пуш блокируется с командой починки:

```
$ git push
submodule-hook: libs/api-clients: коммит e38cb215 (коммит c3a1b2c3) отсутствует на remote сабмодуля — не запушен или удалён force-push'ом;
    запушь сабмодуль: git -C libs/api-clients push
    или переключи указатель на существующий коммит и обнови env.yml
submodule-hook: push заблокирован — висячие коммиты сабмодулей (команды починки выше)
```

Нюансы:

- проверяются сабмодули, закреплённые в `env.yml` рабочей копии; gitlink'и
  незакреплённых сабмодулей хук не видит — закрепи их в конфиге;
- сабмодуль не инициализирован — проверка пропускается с предупреждением
  (fail-open, пуш не блокируется);
- offline и коммит неизвестен даже локально — проверка пропускается с предупреждением;
- `on_error: warn` превращает блокировку в предупреждение;
- успешный пуш молчит: pre-push печатает только предупреждения и ошибки;
- встроенная альтернатива — `git config push.recurseSubmodules check`: та же идея,
  но требует настройки в каждом клоне отдельно и не знает про пины env.yml.

## Установка

```sh
python3 -m venv .venv && . .venv/bin/activate
pip install .          # появится команда submodule-hook
./scripts/install.sh   # поставит .git/hooks/pre-commit и .git/hooks/pre-push
```

`scripts/install.sh` принимает путь к репозиторию аргументом и бэкапит существующие хуки.

Ручной вариант — файл `.git/hooks/pre-commit`:

```sh
#!/bin/sh
exec submodule-hook "$@"
```

и `.git/hooks/pre-push` (git передаёт хуку имя и URL remote аргументами — хук их
игнорирует, список пушемых ссылок приходит на stdin):

```sh
#!/bin/sh
exec submodule-hook --push
```

Вариант для [pre-commit framework](https://pre-commit.com) (локальные хуки, без изоляции окружения):

```yaml
repos:
  - repo: local
    hooks:
      - id: submodule-hook
        name: submodule pin check
        language: system
        entry: submodule-hook
        always_run: true
        pass_filenames: false
      - id: submodule-push
        name: submodule dangling check
        language: system
        entry: submodule-hook --push
        stages: [pre-push]
        always_run: true
        pass_filenames: false
```

## Конфигурация

Всё лежит в самом `env.yml` рядом с секцией `submodules:` — отдельного файла
конфигурации у хука нет. Полный пример — [env.example.yml](env.example.yml):

```yaml
submodules:
  - folder: path/to/submodule_1   # путь сабмодуля от корня, как в .gitmodules
    commit_sha: "12351adf"        # коммит, на котором должен стоять сабмодуль
    lookup_branch: master         # защищённая ветка, куда льются мержи

submodule_hook:                   # необязательная настройка хука (дефолты)
  remote: origin
  fetch: true
  on_error: fail
  skip_merges: true
```

Поля сабмодуля:

- `folder` — путь от корня репозитория; валидируется, что это запись сабмодуля в
  индексе (mode 160000), иначе ошибка конфига; дубли путей отвергаются;
- `commit_sha` — hex-SHA (4–40 символов, короткие можно);
- `lookup_branch` — имя ветки на remote без префикса `origin/`; по умолчанию `master`.

Поля `submodule_hook`:

- `remote` (origin) — откуда fetch-ить lookup-ветки;
- `fetch` (true) — обновлять lookup-ветки при каждом запуске; `--no-fetch` — офлайн,
  по существующим remote-tracking-ссылкам;
- `on_error` (fail) — `warn` пропускает коммит с предупреждением (переходный период);
- `skip_merges` (true) — не срабатывать на merge-коммитах.

Конфиг валидируется при каждом запуске. Путь к файлу перекрывается `--config` или
переменной окружения `SUBMODULE_HOOK_CONFIG`. Остальные аргументы: `--remote`,
`--no-fetch`, `--on-error {fail,warn}`, служебный `--repo`, `-v`, `-q`.
Dry-run не нужен: хук ничего не пишет — только читает и выносит вердикт.

Коды возврата: `0` — норма (предупреждения допустимы); `1` — расхождение конфига
и ветки, коммит блокируется (при `on_error: warn` — нет); `2` — проблемы конфига.

## Поведение, которое стоит знать команде

- **Индекс — источник правды.** Хук сверяет с индексом и закреплённый коммит, и
  состояние сабмодуля — то есть то, что реально уедет в коммит. Если рабочая копия
  разошлась с индексом (изменили `env.yml` или переключили чекаут сабмодуля, но не
  сделали `git add`) — предупреждение с готовой командой.
- **Хук ничего не меняет.** Только читает и блокирует. Починка всегда руками —
  команда в сообщении ошибки.
- **Подтяжка мастера в фичу.** Merge-коммит пропускается (`skip_merges`); если после
  него сабмодуль уехал с `CONFIG`, это всплывёт на первом же обычном коммите —
  с подсказкой «обнови `commit_sha`», а не с откатом сабмодуля.
- **Офлайн.** Fetch не удался — `TARGET` берётся из локальной remote-tracking-ссылки;
  нет и её — мягкая проверка пропускается с предупреждением. Жёсткая проверка
  локальна и работает всегда.
- **Неинициализированный сабмодуль** (`git submodule status` с минусом) — проверки
  работают: ссылка в индексе суперпроекта есть, чекаут не сверяется.
- **`git commit --no-verify`** обходит pre-commit локально, `git push --no-verify` —
  pre-push; серверный валидатор для CI — в [BACKLOG.md](BACKLOG.md).

## Разработка

```sh
pip install -e ".[dev]"
pytest
```

Тесты создают одноразовые git-репозитории с настоящими сабмодулями (bare-репозиторий
как источник + суперпроект) и прогоняют хук целиком: все четыре строки таблицы
решений, офлайн, merge-коммиты, короткие SHA, висячие пуши — включая настоящий
`git push` с установленным хуком.

Обкатать инструмент на живых сценариях (онбординг со свежего клона, осознанный бамп,
висячий пуш, отставший конфиг, force-push в сабмодуле) — на одноразовой песочнице
с двумя «разработчиками»:

```sh
. .venv/bin/activate
./scripts/demo.sh
```
